# 키워드 마스터

네이버 키워드 검색량 · 경쟁강도 분석 서비스. Next.js(App Router) + TypeScript.

## 기능

| 기능 | 설명 | 데이터 출처 |
|---|---|---|
| 키워드 검색량 조회 | PC / 모바일 / 합계 월간 검색수, 모바일 비중 | 네이버 검색광고 API |
| 연관 키워드 추천 | 검색량 상위 100개, 순위 자동 부여 | 네이버 검색광고 API |
| 경쟁강도 분석 | 블로그 문서수 ÷ 검색수 → 5단계 등급 | 검색광고 + 검색 API |
| **상품명 최적화** | 상품명이 어떤 검색어에 걸리는지 계산하고 추가할 단어를 제안 | 검색광고 API (추가 호출 없음) |
| 카테고리별 연관 키워드 | 11개 1depth 분야를 훑어 역추정한 뒤 분야별로 그룹핑 | 쇼핑인사이트 |
| **쇼핑 태그 최적화** | 슬롯 10개에 넣을 태그 후보 추천 + 스마트스토어 정책 규칙 검사 | 검색광고 + 검색어트렌드 |
| 순위 조회 | 키워드 검색 결과에서 내 블로그·카페 글 위치 (최대 1000위) | 네이버 검색 API |
| 검색 추이 | 최근 12개월 상대 검색 지수 | 검색어트렌드 |
| **구매층 프로필** | 성별·연령 비중 | 쇼핑인사이트 |
| **시즌성 지수** | 3년치 월별 추이로 성수기·비수기 자동 판정 | 검색어트렌드 |
| **뉴스 이슈도** | 최신 100건의 발행 밀도로 화제성 판별 | 뉴스 검색 API |
| **쇼핑 분야 후보** | 11개 1depth 분야를 훑어 카테고리 역추정 | 쇼핑인사이트 |
| 즐겨찾기 | 브라우저 localStorage 저장 | – |
| 엑셀 내보내기 | UTF-8 BOM CSV — 키워드 표, 즐겨찾기, 상품명 최적화, 태그 | – |

> ⚠️ **쇼핑(상품) 검색 API 는 없습니다**
> 네이버는 검색·데이터랩 API 를 `developers.naver.com` 에서 **NAVER API HUB(네이버 클라우드 플랫폼)** 로 옮겼고, 구 플랫폼은 신규 등록이 막혔습니다. 신규 사용자는 API HUB 를 써야 합니다.
> 그 과정에서 **쇼핑(상품) 검색은 어느 쪽에도 남지 않았습니다** — API HUB 에도 없고, 살아 있는 구 플랫폼 키에도 없습니다. 그래서 이 앱은 **등록 상품수·쇼핑 경쟁도·상품 카테고리 분류를 아예 다루지 않습니다.** 조회할 수 없는 값을 빈칸으로 남겨 두는 대신 기능에서 뺐습니다.
> 쇼핑 쪽 신호가 필요한 곳(구매층, 시즌성, 분야 추정)은 **쇼핑인사이트**(데이터랩)로 대신합니다. 이쪽은 정상 동작합니다.

## 2. 환경변수 설정

```bash
copy .env.local.example .env.local
```

`.env.local` 을 열어 아래 두 종류의 키를 채웁니다. **키가 없어도 앱은 데모 데이터로 동작**하므로 UI를 먼저 확인한 뒤 채워도 됩니다.

### 2-1. 네이버 검색광고 API (검색량 · 연관 키워드)

1. <https://searchad.naver.com> 가입 (사업자 없이 개인도 가능)
2. 우측 상단 **도구 → API 사용 관리**
3. **네이버 검색광고 API 라이선스** 발급
4. 화면에 표시되는 값을 옮겨 적습니다

| 화면 표기 | .env.local 변수 |
|---|---|
| CUSTOMER_ID | `NAVER_AD_CUSTOMER_ID` |
| 액세스라이선스 | `NAVER_AD_ACCESS_LICENSE` |
| 비밀키 | `NAVER_AD_SECRET_KEY` |

### 2-2. NAVER API HUB (문서수 · 경쟁강도 · 추이) — 신규 사용자

1. <https://www.ncloud.com> 가입
2. 콘솔에서 **Services → NAVER API HUB → 이용 신청**
3. 발급된 Client ID / Client Secret 을 `NCP_API_KEY_ID`, `NCP_API_KEY` 에 입력

호출 규격 (코드에 반영됨):

| 항목 | 값 |
|---|---|
| 호스트 | `https://naverapihub.apigw.ntruss.com` |
| 인증 헤더 | `X-NCP-APIGW-API-KEY-ID` / `X-NCP-APIGW-API-KEY` |
| 블로그 검색 | `GET /search/v1/blog?query=…&display=1&format=json` |
| 쿼터 | 검색 월 775,000회(통합), 데이터랩 각 월 50,000회, 50 RPS |
| 요금 | 현재 무료 체험, 향후 종량제 예정 |

**쇼핑(상품) 검색은 API HUB 에도, 구 플랫폼 키에도 없습니다.** 이 앱이 상품수·쇼핑 경쟁도·상품 카테고리를 다루지 않는 이유입니다.

### 2-2B. 구 developers.naver.com 키 (있는 경우에만)

2025년 이관 전에 발급받아 아직 살아 있는 키가 있다면 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` 에 넣으면 됩니다. 블로그·카페·뉴스 검색과 데이터랩이 동작합니다. 두 키가 다 있으면 API HUB 가 우선 사용됩니다.

신규 발급은 불가능합니다 — 등록 화면의 사용 API 목록에서 `검색`·`데이터랩`이 제거되었고, 기존 앱에서 선택해도 "신규로 등록할 수 없는 API가 선택되었습니다" 오류가 납니다.

### 리전을 서울로 고정한 이유

기본값(`iad1`, 미국 동부)으로 두면 호출이 전부 네이버(한국)로 나가면서 왕복 지연이 그대로 응답 시간이 됩니다. `X-Vercel-Id` 가 `icn1::iad1::…` 이면 엣지만 서울이고 함수는 미국이라는 뜻입니다.

100행 분석 실측 (캐시 없음):

| 설정 | 소요 |
|---|---|
| `iad1` + 동시 5 | 20.0초 |
| `iad1` + 동시 20 | 7.0~9.3초 |
| **`icn1` + 동시 20** | **4.0~4.6초** (로컬과 동일) |

지금은 네트워크가 아니라 호출 게이트(100 × 40ms = 4초)가 하한입니다.

## 지표 읽는 법

**경쟁강도 = 블로그 발행 문서수 ÷ 월간 검색수**

문서수는 **따옴표를 씌운 정확일치 검색**으로 셉니다. 네이버 검색은 따옴표가 없으면 형태소 단위로 느슨하게 매칭해서, 조합형·롱테일 키워드일수록 실제와 크게 벌어지기 때문입니다.

| 쿼리 | 그냥 검색 | 정확일치 |
|---|---|---|
| 유아용 실내 미끄럼방지 양말 | 64,139 | **0** |
| 여성여름원피스 | 388,278 | **1,816** |
| 린넨원피스 | 261,123 | **65,092** |

**블로그만 셉니다.** 카페 검색은 따옴표를 무시해서(`여성여름원피스` 250,406 → 정확일치 250,399) 나온 수치가 해당 키워드를 노린 글 수가 아니고, 상위 결과도 키워드와 무관한 글이 섞입니다. 쇼핑(상품) 검색은 네이버가 API 자체를 제공하지 않습니다.

| 값 | 등급 | 의미 |
|---|---|---|
| ≤ 0.1 | 최고 | 검색량 대비 문서가 거의 없음 — 바로 노려볼 만함 |
| ≤ 0.5 | 좋음 | 진입 유리 |
| ≤ 1 | 보통 | 콘텐츠 품질로 승부 |
| ≤ 5 | 나쁨 | 상위 노출 어려움 |
| > 5 | 최악 | 사실상 포화 |

**문서수는 표에 보이는 행 전부에 붙입니다.** 예전에는 상위 20개만 조회해서 나머지는 `–` 로 남았는데, 경쟁이 낮은 롱테일 키워드는 대개 검색량 순위 아래쪽에 있어 정작 찾아야 할 키워드에 등급이 없었습니다. 키워드당 검색 API 1회를 쓰며, 100행 기준 5초 안팎입니다.

연관 키워드는 검색광고 API 가 수백 개를 돌려주고(`여성여름원피스` 592개, `캠핑의자` 927개) 그중 **검색량 상위 100개만** 표에 올립니다. 몇 개 중 몇 개인지는 표 제목 아래에 적어 둡니다.

### 마스킹된 검색수 (`*` 표시)

네이버는 월 검색수가 10 미만이면 `< 10` 으로 가립니다 (`여성여름원피스` 연관 키워드 592개 중 146개). 이때 표시하는 값은 실측치가 아니라 **상한**이라서:

- 총 검색수는 `< 20` 처럼 적습니다 (PC·모바일 각각 상한 10).
- 분모가 상한이면 경쟁강도는 **하한**이 되므로 `≥ 0.00` 처럼 적고, 실제 등급은 표시된 것보다 나쁠 수 있습니다.
- **"노려볼 만한 키워드" 집계에서 뺍니다.** 검색수 20(실제로는 2일 수도 있는), 문서수 0인 키워드가 `경쟁강도 0.00 · 최고` 로 잡혀 황금 키워드처럼 보이던 문제 때문입니다.

CSV 로 내보낼 때는 숫자 칸에 `<`·`≥` 를 섞지 않고 `검색수 마스킹`·`경쟁강도 하한여부` 열로 따로 뺍니다 (엑셀에서 텍스트가 되면 정렬·수식이 깨지므로).

## 상품명 최적화 읽는 법

네이버쇼핑 랭킹은 **적합도 · 인기도 · 신뢰도**로 갈립니다. 인기도(클릭·판매·리뷰)와 신뢰도는 도구가 건드릴 수 없고, **내 상품의 실제 순위도 조회할 수 없습니다** — 네이버가 쇼핑 상품 검색 API 를 제공하지 않습니다(`search/v1/shop` → 404). 이 탭이 다루는 건 적합도 하나, 그중 판매자가 직접 고칠 수 있는 상품명입니다. 신규 상품에서 가장 크게 작용하는 지점이지만 전부는 아닙니다.

**계산 방식** — 네이버쇼핑은 상품명을 단어 묶음으로 보고 검색어의 단어가 전부 들어 있으면 매칭합니다. 검색광고 API 의 연관 키워드는 공백이 제거된 채 오므로(`여성여름원피스`), "포함"이 아니라 **"상품명 토큰들로 빈틈없이 분해 가능한가"** 를 word-break DP 로 판정합니다. 토큰 `{여성, 여름, 원피스}` 는 `여성여름원피스` 를 커버하지만 `{여성, 원피스}` 만으로는 커버하지 못합니다.

`린넨원피스` 시드(연관 키워드 100개) 실측:

| 상품명 | 글자 | 걸리는 검색어 | 커버 검색량 |
|---|---|---|---|
| 린넨 원피스 | 6자 | 1개 | 18,540 |
| 린넨 여름 원피스 여성 | 12자 | 6개 | 120,260 |
| 여성 여름 린넨 롱 원피스 반팔 브이넥 | 21자 | 13개 | 152,110 |

단어 하나의 한계 이득도 나옵니다 — `여름` 2글자가 **+65,150**(글자당 32,575), `여성원피스` 5글자는 +24,670. 글자 예산이 한정된 상황에서 뭘 넣을지가 수치로 갈립니다.

### 가드레일이 본체입니다

검색량만 최대화하면 이런 조합이 1등으로 올라옵니다:

```
린넨 원피스 여름 플리츠 아이팜므 블라우스 여성  →  커버 10개 / 292,830
```

`아이팜므`·`디얼마미`는 **타사 브랜드**, `블라우스`는 **다른 품목**입니다. 둘 다 네이버가 어뷰징으로 보는 항목이라 따를수록 순위가 떨어집니다. 그래서 후보를 이렇게 좁힙니다.

**상품유형(head) 추정** — 한국어 복합 키워드는 뒤쪽이 품목입니다(`린넨원피스` → `원피스`). 시드의 접미사 중 연관 키워드의 접미사로 많이 등장하는 것을 품목으로 잡되, **최댓값의 90% 이상인 것 중 가장 긴 것**을 고릅니다. 짧은 접미사는 긴 접미사를 항상 포함해서(`드셋` ⊇ `헤드셋`) 개수만 보면 늘 짧은 쪽이 이기고, 오타 키워드 하나로도 뒤집히기 때문입니다 — 실측으로 `게이밍헤드셋`에서 `무선해드셋`(해/헤 오타) 때문에 `드셋` 36개가 `헤드셋` 35개를 앞질러 품목이 `드셋`으로 잡혔습니다. 그렇게 고른 head 로 **같은 품목 키워드에서 head 를 뗀 수식어만** 후보에 넣습니다. 이 규칙 하나가 브랜드와 다른 품목을 동시에 걸러 냅니다.

| 시드 | 추정 품목 | 걸러진 것 | 남은 후보 |
|---|---|---|---|
| 린넨원피스 | 원피스 (74/100) | 아이팜므, 디얼마미, 나노세컨, 블라우스, 여름스커트 | 플리츠, 여름, 여성, 휴양지, 쉬폰, 나시 |
| 캠핑의자 | 의자 (8/100) | 부산놀거리, 캠핑카, 원터치텐트, 돗자리 | 좌식, 낚시, 경량캠핑, 접이식캠핑, 휴대용 |
| 강아지사료 | 사료 (47/100) | 동물병원, 강아지간식, 췌장염 | 강아지, 고양이, 강아지알러지, 노견, 대형견 |

여기에 알려진 상표·홍보문구·판매처명은 하드 차단하고(`brand-data.ts` 목록, `tag-rules.ts`·`product-name.ts`·`tag-suggest.ts` 공유), 단독으로도 검색되는 단어에는 `⚠` 를 붙입니다. 다만 **모든 브랜드를 자동 판별하지는 못합니다** — `나우`(사료), `샤크`(청소기)처럼 수식어 자리에만 오는 브랜드는 못 걸러 내므로 낯선 단어는 직접 확인해야 합니다.

목록에 없는 브랜드를 만나면 화면의 **"직접 확인한 타사 브랜드 추가"** 칸에 적으면 그 자리에서 후보·태그·상품명 검사 전부에 반영됩니다. 브라우저 localStorage 에 저장되어 다음 방문에도 남습니다 — 코드를 고치지 않고도 판매자가 스스로 목록을 넓혀 갈 수 있습니다. 자주 마주치는 브랜드라면 `brand-data.ts` 에 아예 추가해 모두에게 적용되게 합니다.

상품명 자체는 특수문자·홍보문구·판매처명·타사 상표·중복 단어·길이(권장 50자 / 최대 100자)·품목명 누락을 검사합니다.

### 50자는 지키는 게 맞습니다 — 이유는 "가중치"가 아니라 "제재"

상품명 입력란은 100자까지 받지만 네이버는 50자를 권장합니다. **그 이유가 흔히 잘못 알려져 있어** 근거를 적어 둡니다.

상품등록 화면이 직접 경고합니다:

> 글자수 50자 이내 입력을 권장합니다.
> 상품명을 검색최적화 가이드에 맞게 입력하면 검색 노출에 도움이 될 수 있으며, **가이드에 맞지 않을 경우 별도 고지 없이 제재될 수 있습니다.**

쇼핑 검색 SEO 가이드도 "50자 내외의 텍스트 사용을 권장 (최대 100자 허용)", "**50자 이상은 어뷰즈로 판단될 확률이 높음**" 으로 안내합니다.

즉 51자부터 랭킹 점수가 조금씩 깎이는 **연속적 감점이 아니라, 어뷰징 판정이라는 이진적 위험**입니다. 이 앱도 예전에는 "50자를 넘으면 뒤쪽 단어의 가중치가 떨어진다"고 적었는데, 네이버가 밝힌 적 없는 근거 없는 서술이라 지웠습니다.

**지키는 비용은 사실상 0입니다.** 커버리지 곡선이 그걸 보여 줍니다.

| 상품명 | 글자 | 커버 검색량 | 직전 대비 |
|---|---|---|---|
| 린넨 원피스 | 6자 | 18,540 | – |
| 린넨 여름 원피스 여성 | 12자 | 120,260 | +101,720 (6자당) |
| 여성 여름 린넨 롱 원피스 반팔 브이넥 | 21자 | 152,110 | +31,850 (9자당) |

20자 부근에서 이미 완만해집니다 — **같은 품목의 쓸 만한 수식어가 50자보다 훨씬 먼저 고갈**되기 때문입니다. 50자를 넘겨 얻는 추가 커버리지는 대개 다른 품목이나 브랜드 단어에서 나오는데, 그건 어차피 후보에서 걸러 냅니다. 얻는 것은 작고 잃을 수 있는 것은 큰 거래입니다.

그래서 화면은 50자를 **글자 예산**으로 다룹니다. 길이 카드에 `50자까지 N자 남음`(초과 시 `권장 50자를 N자 넘음`)을 표시하고, 넣으면 예산을 넘는 추천 단어는 흐리게 + `50자 초과` 로 표시합니다. 막지는 않습니다 — 다른 단어를 빼고 넣는 선택은 판매자 몫입니다.

> ⚠️ **실측하지 못한 부분** — "51자 상품이 실제로 순위가 밀리는가"는 확인할 방법이 없습니다. 쇼핑 상품 검색 API가 없어(`search/v1/shop` → 404) 순위를 조회할 수 없기 때문입니다. 위 판단은 네이버 공식 안내와 커버리지 곡선에 근거한 것이지 순위 실험 결과가 아닙니다.

> 계산이 전부 순수 함수라 **서버를 거치지 않습니다.** 이미 받아 둔 연관 키워드로 타이핑하는 즉시 다시 세며, API 쿼터를 쓰지 않습니다.

**엑셀 내보내기** — 요약·검사 결과·걸리는 검색어·추천 단어·못 걸린 검색어를 맨 앞 `구분` 열로 구분해 한 파일에 담습니다. 엑셀에서 그 열로 필터를 걸면 섹션별로 볼 수 있습니다. 화면은 추천 단어와 못 걸린 검색어를 12개씩만 보여 주지만 **CSV 에는 전부 들어갑니다** (`린넨원피스` 기준 추천 62개·미커버 91개). 화면의 `⚠` 는 숫자 열이 텍스트가 되지 않도록 `확인필요` 열로 뺐습니다.

## 쇼핑 태그 최적화 읽는 법

스마트스토어 태그는 **상품당 10개**가 전부입니다. 그래서 문제는 "이 태그가 괜찮은가"(검사)가 아니라 **"그 10칸을 어디에 쓸 것인가"**(배분)입니다. 기존 검사기 위에 후보 추천을 얹었습니다.

**후보에서 빼는 것 세 가지**

1. **상품명이 이미 걸어 둔 검색어** — 태그로 또 넣으면 슬롯만 낭비입니다. 상품명 최적화 탭에 입력한 상품명을 그대로 받아 계산합니다.
2. **다른 품목** — 상품유형(head) 추정은 상품명 최적화와 같은 방식입니다.
3. **정책 위반** — 홍보문구·판매처명·알려진 타사 상표.

**추천점수 = 월간 검색수 × 경쟁 가중치** (최고 1.0 · 좋음 0.8 · 보통 0.5 · 나쁨 0.25 · 최악 0.1). 검색량만 보면 이미 포화된 대형 키워드에 10칸을 다 쓰게 됩니다. `린넨원피스` 실측:

| 슬롯 | 경쟁 가중 적용 | 검색량만 볼 때 |
|---|---|---|
| 1 | 플리츠원피스 (62,040 · 나쁨) | 플리츠원피스 |
| 2 | **샤틴원피스 (10,150 · 보통)** | 휴양지원피스 (최악) |
| 3 | **바스락원피스 (11,270 · 나쁨)** | 쉬폰원피스 (최악) |

`샤틴원피스`는 검색량이 절반이지만 경쟁이 **보통**이라 실제 노출 가능성이 훨씬 높습니다.

### 한 번에 채워 주는 버튼은 일부러 없습니다

만들었다가 뺐습니다. `여름원피스`로 돌려 보니 상위 10개에 **`유니클로원피스`·`로엠원피스`** — 타사 브랜드가 들어갔습니다. 상표 목록을 늘려 이 둘은 잡았지만, 목록은 완전해질 수 없습니다.

키워드 데이터만으로 브랜드를 판별하는 방법도 시도했습니다. 상품명 최적화에서 쓰는 "수식어가 단독으로도 검색되는가" 규칙을 태그에 적용해 봤더니 역효과였습니다.

| | 결과 |
|---|---|
| 못 잡은 브랜드 | 유니클로, 나우, 샤크, 신일, 한끼뚝딱, 라비앙독 |
| 잘못 잡은 정상 수식어 | 애견, 물걸레, 노령견, 가수분해 |

그래서 이 규칙은 태그에 쓰지 않고, **체크박스를 하나씩 누르게** 했습니다. 10번 클릭하는 마찰이 각 태그를 읽고 넘어가게 만드는 장치입니다. 걸러 낸 뒤에도 대상이 다른 후보(강아지 상품에 `고양이사료`)나 모르는 브랜드가 남으므로 **최종 판단은 사람이 해야 합니다.**

### 후보가 적게 나올 때

`캠핑의자`는 후보가 **4개**뿐입니다 — 연관 키워드 100개 중 91개가 다른 품목(부산놀거리·캠핑카·텐트)이기 때문입니다. 10칸을 못 채우는 게 정상이고, 이럴 땐 더 좁은 키워드로 다시 분석해야 합니다.

## 구매층 · 시즌성 · 이슈도 읽는 법

**시즌성** — 최근 3년 월별 검색 추이에서 같은 달끼리 평균을 내 계절 패턴만 남기고, 변동계수(표준편차 ÷ 평균)로 등급을 매깁니다. 임계값은 실데이터로 맞췄습니다.

| 키워드 | 변동계수 | 등급 | 성수기 |
|---|---|---|---|
| 패딩 | 1.25 | 뚜렷 | 10·11·12월 |
| 린넨원피스 | 0.98 | 뚜렷 | 6·7·8월 |
| 수영복 | 0.30 | 뚜렷 | 6·7·8월 |
| 화장지 | 0.21 | 보통 | – |
| 무선청소기 | 0.12 | 없음 | – |

이 방식은 단어 목록 매칭이 놓치던 키워드를 잡아냅니다. `린넨원피스`에는 시즌 단어가 없지만 실제로는 여름에 몰립니다. 쇼핑 태그 검사도 이 값을 쓰며, 지금이 비수기면 경고를 냅니다.

**진행 중인 달은 계산에서 뺍니다.** 데이터랩은 조회 종료일이 월 중간이어도 그 달을 한 칸으로 돌려주는데, 값은 지나간 며칠치뿐입니다 (8월 7일에 조회한 `수영복`: 7월 47.7 → 8월 9.9). 이 칸을 예년 8월과 평균 내면 이번 달 지수가 눌려 성수기·비수기 판정이 뒤집힙니다. 실측 비교:

| 키워드 | 포함했을 때 | 제외했을 때 |
|---|---|---|
| 텐트 | 성수기 5·9·10월 · 지금 **보통** | 성수기 8·9·10월 · 지금 **성수기** |
| 화장지 | 성수기 1·9·10월 · 지금 **보통** | 성수기 8·9·10월 · 지금 **성수기** |
| 제습기 | 지금 **비수기** | 지금 **보통** |
| 홍삼스틱 | 지금 **비수기** | 지금 **보통** |
| 캠핑의자 | 성수기 5·6·9월 | 성수기 6·8·9월 |
| 수영복 | 8월 지수 59.1 | 8월 지수 75.5 |

차트에서는 이 달을 지우지 않고 **점선**으로 끊어 그리고, 증감률도 확정된 달끼리만 계산합니다. 구매층(성별·연령)과 쇼핑 분야 후보의 '데이터가 잡힌 개월 수'에서도 같은 이유로 뺍니다.

날짜는 **KST 기준**으로 만듭니다. `toISOString()` 은 UTC 라서 한국 시간 오전 9시 이전에는 조회 구간이 하루 밀리고, `setMonth()` 로 월을 빼면 31일에서 없는 날짜로 넘어갑니다(5월 31일 −3개월 → 3월 3일).

**뉴스 이슈도** — "최근 30일 몇 건"으로는 발행량이 많은 키워드에서 변별이 안 됩니다(`수영복`은 받아온 100건이 전부 30일 이내). 그래서 **최신 100건이 걸쳐 있는 기간**으로 하루당 발행 밀도를 계산합니다. 검색량이 급등했을 때 이슈성인지 실수요인지 가르는 데 씁니다.

**쇼핑 분야 후보** — 쇼핑인사이트는 카테고리 코드를 입력으로 받으므로, 11개 1depth 분야를 모두 훑어 어디서 클릭이 잡히는지로 역추정합니다. 지수(`ratio`)는 응답 하나 안에서 최댓값을 100으로 잡는 상댓값이라 **분야끼리 비교할 수 없어서**, 데이터가 잡힌 개월 수로 순위를 매기고 후보를 복수로 보여줍니다. `수영복`이 스포츠/레저와 출산/육아 양쪽에 잡히는 건 오류가 아니라 실제로 걸쳐 있는 것입니다.

**카테고리별 연관 키워드** — 위 역추정을 상위 20개 키워드에 각각 돌려 분야별로 묶습니다. 키워드당 11회 호출이라 자동 실행하지 않고 **버튼을 눌렀을 때만** 돕니다 (20개 기준 약 220회, 10초 내외). 조회 결과는 6시간 캐시됩니다.

호출은 **초당 25회로 제한**해 두었습니다. API HUB 한도는 50 RPS 인데, 제한을 넘긴 호출이 "데이터 0개월"로 취급되면 엉뚱한 분야가 1위가 되기 때문입니다 (실제로 `강아지사료`가 패션잡화로, `캠핑의자`·`홍삼스틱`이 미분류로 나왔습니다). 11곳 중 3곳 이상 실패하면 결과를 내지 않고 오류를 띄웁니다.

### 호출 한도 (`lib/ratelimit.ts`)

한도가 **API 키 단위 50 RPS** 라서 검색·데이터랩·쇼핑인사이트가 한 통에 담깁니다. 예전에는 쇼핑인사이트만 스스로 속도를 줄였는데, 키워드 분석(문서수)과 카테고리 분류가 겹쳐 돌면 합계로 한도를 넘겼습니다. 지금은 **모든 API HUB 호출이 같은 게이트**를 지나고, 429·5xx 는 물러섰다가 두 번까지 다시 시도합니다.

실측 (블로그 검색 동시 호출):

| 동시 호출 | 결과 |
|---|---|
| 40 | 40 성공 |
| 120 | 83 성공 / 37 실패 `429 Rate Limited` |

게이트를 넣은 뒤 키워드 분석(60회) + 카테고리 분류(33회) 를 동시에 돌려도 93회 전부 성공합니다 (4.7초).

## 서버리스와 캐시

`cache.ts` 는 두 단으로 쌓여 있습니다.

- **L1 — 프로세스 메모리**: 항상 켜져 있고 왕복이 없어 빠릅니다. 하지만 Vercel
  서버리스 함수는 요청마다 다른 인스턴스가 뜰 수 있어서, 인스턴스 사이에는
  이 메모리가 공유되지 않습니다. 콜드스타트가 나면 "6시간 캐시"였던 것이
  실제로는 그때그때 미스가 나는 구조였습니다.
- **L2 — Redis (선택)**: `KV_REST_API_URL`/`KV_REST_API_TOKEN`(Vercel KV) 또는
  `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`(Upstash 직접 연결) 이
  설정되면 자동으로 켜집니다. 인스턴스가 바뀌어도 이 저장소는 공유되므로
  캐시가 실제로 6시간을 버팁니다. 두 변수 다 없으면 `kv.ts` 는 조용히
  비활성 상태로 남고 앱은 L1 만으로 지금까지처럼 동작합니다 — **로컬
  개발에는 Redis 가 필요 없습니다.**

Redis 호출이 실패하거나(네트워크 문제, 토큰 만료) 타임아웃(2초)에 걸려도
요청은 죽지 않습니다. 읽기 실패는 직접 계산으로, 쓰기 실패는 "이번 응답은
정상, 다음 요청부터 다시 캐시 미스"로 조용히 물러납니다.

붙이는 방법 — Vercel 대시보드에서 **Storage → Create Database →
Marketplace Database Provider → Upstash for Redis**(무료 티어 있음)를 만들면
`KV_REST_API_URL`/`KV_REST_API_TOKEN` 이 프로젝트 환경변수에 자동으로
채워집니다. 새 패키지는 추가하지 않았습니다 — Upstash REST API 는 순수
HTTP 라 Next.js 런타임의 전역 `fetch` 로 충분합니다.

> ⚠️ 레이트리밋(`ratelimit.ts`)은 같은 이유로 인스턴스 사이에 공유되지
> 않지만 그대로 뒀습니다. 이 게이트는 **한 요청 안에서 부채꼴로 퍼지는
> 내부 호출**(예: `/api/analyze` 하나가 문서수 조회 100회로 퍼지는 것)을
> 25 RPS 로 눌러 주는 용도라 인스턴스 하나 안에서는 지금도 제대로 동작하고,
> 여러 인스턴스가 겹쳐 429 가 나더라도 `withRetry` 가 두 번까지 재시도합니다.
> 여러 사용자가 동시에 몰리는 서비스가 아니라면 Redis 기반 분산 리미터로
> 바꾸는 비용 대비 실익이 낮아 보류했습니다.

## 문제 해결

**`errorCode: 024` / `Scope Status Invalid : Authentication failed`**

구 developers.naver.com 키를 쓸 때 납니다. 키 자체는 맞지만 **애플리케이션에 검색 API 권한이 없는 것**입니다. 그런데 이제 그 권한을 새로 추가할 수 없습니다 (아래 참조). **NAVER API HUB 키로 전환하세요.**

**`신규로 등록할 수 없는 API가 선택되었습니다`**

developers.naver.com 에서 사용 API 에 `검색`·`데이터랩`을 추가하려 할 때 납니다. 네이버가 해당 API 를 NAVER API HUB 로 이관하면서 구 플랫폼의 신규 등록을 막았기 때문이며, 우회 방법은 없습니다. 신규 등록 화면의 사용 API 목록에는 네이버 로그인·인증서·전자문서·네이버페이 배송지·카페·캘린더·캡차만 남아 있습니다.

**검색광고 API가 401**

`NAVER_AD_CUSTOMER_ID` 가 액세스라이선스를 발급받은 그 광고계정의 번호인지 확인하세요. 한 아이디에 광고계정이 여러 개면 번호가 각각 다릅니다.

## 알아 두어야 할 제약

- **쇼핑 태그 등록 가능 여부**: 네이버는 이를 조회하는 공개 API를 제공하지 않습니다. 이 앱은 스마트스토어 상품등록 정책(길이·특수문자·홍보문구·판매처명·타사 상표)을 규칙으로 구현하고, 월간 검색수와 3년치 추이로 계산한 시즌성을 근거로 **추정**합니다. 등록 상품수·카테고리 집중도는 쇼핑 검색 API 가 없어 근거로 쓸 수 없습니다. 최종 확인은 스마트스토어 상품등록 화면에서 하세요.
- **순위 조회**: 네이버 검색 오픈 API 결과 순서 기준이며 블로그·카페만 지원합니다(쇼핑 검색 API 없음). 통합검색 화면의 VIEW·스마트블록 노출 순위와는 다를 수 있습니다.
- **검색 추이**: 데이터랩은 절대 검색수가 아니라 기간 내 최고값을 100으로 한 상대 지수입니다. 마지막 칸은 진행 중인 달이라 값이 낮게 잡히며, 차트에 점선으로 구분하고 시즌성 계산에서는 뺍니다.
- **검색수 마스킹**: 월 10회 미만은 `< 10` 으로 가려집니다. 이 키워드의 검색수·경쟁강도는 상한/하한이지 실측치가 아닙니다.
- **검색광고 API**: 초당 호출 제한이 있습니다. 여러 키워드를 연속 조회하면 429가 날 수 있으며, 6시간 캐시로 완화했습니다.
- 두 API 모두 네이버 이용약관을 따릅니다. 수집 데이터를 재판매하거나 대량 크롤링에 쓰지 마세요.
